# monthly-payroll-release-gate

## 位置づけ

- `hr-monthly`（司令塔・進行管理）と `ax-kintai`（生成・突合の実体）の**間**に立つ最終ゲート。
- 目的は、バラバラに出ている実行結果・警告・突合差分・例外承認を1つの固定フォーマットに
  まとめ、「給与確定OK」を出す前に人間が一目で判断できる状態にすること。
- 生成・突合ロジックそのものはここでは持たない。実行は必ず `ax-kintai` / `kintai-check` /
  `payroll-attendance-processor`（Codex側スクリプト）に委ね、このスキルは**結果の集約と
  ゲート判定のみ**を行う。

## 実行手順

1. 対象月（YYYYMM）をユーザーと確認する（前月データでの誤判定防止）。
2. 台帳ファイルの場所: `C:\Users\kuwata\work\payroll-checks\リリースゲート_YYYYMM.md`
   なければ下記テンプレートから新規作成する。**過去月の台帳は編集しない。**
3. 以下を集めて台帳に記入する。実行済みでない項目は「未実行」と明記し、存在しない値を
   推測で埋めない：
   - 入力ファイル一覧（勤怠元データ・支給控除一覧・変動データのパスと最終更新日時）
   - 実行コマンドと実行日時（`generate_ax_kintai.py --month` / `kintai_kyuyo_check.py` /
     `check_hendo_vs_kyuyo.py` / `build_attendance_outputs.py`）
   - 各出力の行数・列数（期待値: 5区分・一般アルバイト=26列 / フレックス=35列 /
     60時間超過=6列。`ax-kintai` 参照）
   - `attendance_processing_report.json` の warnings（Bルート使用時）
   - 突合差分件数（`kintai_kyuyo_check.py` / `check_hendo_vs_kyuyo.py`）。0件が正常
   - 差分が残る場合: `ax-kintai` §6の既知の正当な例外に該当するか。該当しなければ
     `cross-check` スキルでCodexにセカンドオピニオンを取った記録（依頼日時・要旨・結論。
     機微データは必ずマスキングして渡す）
   - 承認欄（担当者名・承認日時。**AIは代筆しない**）
4. 台帳の全項目が「0件／例外承認済み／確認済み」で埋まって初めて「送付可」と報告する。
   1つでも未確認・未実行・説明不能な差分があれば「送付不可」として理由を明記する。

```markdown

|---|---|---|

## 実行ログ

|---|---|---|

## 出力検証
| 出力 | 行数 | 列数 | 期待列数 | OK/NG |
|---|---|---|---|---|

## 警告（attendance_processing_report.json）
-

## 突合差分
| 突合 | 差分件数 | 内容 |
|---|---|---|

## 未解決差分の例外承認
| 項目 | 該当例外 or Codexセカンドオピニオン結論 | 承認者 |
|---|---|---|

## 最終承認
- 判定: 送付可 / 送付不可
- 承認者:
- 承認日時:
```

## 安全ルール

- ここでの「送付可」はAIによる技術的検証結果であり、送付・給与確定の最終意思決定は必ず人間が行う。
- 台帳は事実（コマンド結果・件数）のみを記録する。憶測での「問題なし」は書かない。
- 機微データ（給与額・個人名）をCodexに渡す場合は必ずマスキングする
  （`ax-kintai` §7・`hr-monthly` STEP5の既存ルールを踏襲）。

## hr-monthlyとの接続

`hr-monthly` STEP5（支給控除一覧との突合検証）の最後で、このスキルを呼んで台帳を
生成・更新してからSTEP6（月次資料）に進む。STEP5で「原因を特定しきれない差分」が
出た場合は、本台帳の「未解決差分の例外承認」欄に記録する。

## 完了判定

台帳の全項目が確認済みで、最終承認欄に承認者・日時が入るまで「完了」としない。

## 自己改善プロトコル（毎回実行）

このスキルは Sonnet 5 での実行を前提に手順を明示している。
判断に迷ったら本文の規則のみに従い、推測で進めず不明点はユーザーに質問する。

スキル実行の最後に必ず確認する:
1. ユーザーからの訂正・追加指示があったか。手順どおりに進まなかった箇所
   （パス変更・ファイル形式変更・コマンドエラー等）はあるか
2. あれば、このSKILL.mdの該当箇所を直接修正するか、下の改善ログに1行追記する
   （形式: `- YYYY-MM-DD: [事象] → [変更内容]`）
3. 改善ログが10行を超えたら本文に統合してログを整理する

修正はClaude自身が行ってよい（承認不要）。手順の意味を変える大きな変更のみ一言報告する。
